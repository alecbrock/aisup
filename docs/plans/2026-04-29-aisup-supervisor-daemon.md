## Summary

**Goal:** Build `aisup`, a Node.js/TypeScript daemon that supervises AI coding sessions with automatic multi-account failover, Slack remote control, workflow skill propagation, and a status CLI. MVP scope covers PRD Phase 1 features: A (daemon), B (account selection), C (proactive failover), D₁ (reactive recovery core), E (Slack remote control), I (event journal + CLI), J (workflow skill propagation).

**Architecture:** Daemon process manages tmux sessions (tmux-native — no node-pty). Runner commands execute directly in tmux; daemon monitors via `pipe-pane` streaming output and `capture-pane` snapshots, and sends input via `send-keys`. Sessions survive daemon restarts. Independent monitoring loops (rate-limit, health, recovery, idle) run on separate intervals. Slack Socket Mode provides per-session remote control channels. JSONL event journal provides observability. CLI subcommands talk to daemon via HTTP API on localhost.

**Tech Stack:** Node.js 22+, TypeScript, tmux, commander, strip-ansi (ESM, wraps ansi-regex), @slack/bolt (Socket Mode), @slack/web-api, fastify, js-yaml, vitest.

**Session Identity Model:** Two distinct IDs:
- `aisup_session_id` — UUID generated at `aisup start`. Stable for the logical session's entire lifetime — never regenerated by failover, same-account restart, or daemon restart. Used for tmux session name (`aisup-<first8>`), Slack channel name, pipe-pane log path, state directory, and internal state.
- `claude_session_id` — Emitted by Claude/Pilot in statusline tap JSON. Used for `--resume` flag and transcript migration. Discovered only by matching telemetry to the active `aisup_session_id` using launch time, current account, and resolved cwd/project slug — never by taking the freshest account telemetry file.
- Mapping stored in session state: `~/.aisup/sessions/<aisup_session_id>/state.json`.

## Scope

### In Scope (MVP / Phase 1)

- Daemon process with manual start/stop (`aisup daemon start/stop`)
- Session controller: tmux session creation, send-keys input, capture-pane output monitoring
- Account registry: YAML config parsing, usage scoring from statusline tap files
- Smart account selection at session launch
- Proactive rate-limit failover: 85%/95% thresholds, full switch sequence (snapshot → stop → migrate → resume)
- Reactive recovery: PTY 429 regex detection, process crash restart, circuit breaker (3 failures)
- Slack integration: per-session channel, bidirectional message relay, control commands (!interrupt, !status, !cmd)
- Event journal: JSONL append-only log with structured schema
- CLI: `aisup daemon start|stop`, `aisup start`, `aisup stop`, `aisup attach`, `aisup status`, `aisup log`, `aisup accounts`, `aisup failover --to <account>`
- Workflow skill propagation: detect active skill from PTY output, propagate on resume
- Runner abstraction: configurable command (pilot/claude) via YAML config
- Statusline store: reads existing tap files from `/tmp/pilot-failover/` (no hook installation)

### Slack Is Optional

Slack integration (Tasks 9-10) is part of MVP scope but is **opt-in**. The daemon starts and operates fully without Slack when `slack.enabled: false` (the default). `aisup doctor` reports Slack as optional. All core failover, monitoring, and CLI features work independently of Slack.

### Session Cardinality — MVP Scope

MVP supports **one non-terminal or recoverable logical session at a time**. `aisup start` is allowed only when no persisted session exists, or the only persisted session is terminal `STOPPED` and has no live tmux session. `CREATING`, `ACTIVE`, `SWITCH_PENDING_AT_IDLE`, `SWITCHING`, `STOPPING`, and `EXHAUSTED` all reserve the single-session slot. Multi-session support (session picker, session ID args on all CLI commands) is Phase 2.

### EXHAUSTED Handling — MVP Scope

MVP implements minimal EXHAUSTED handling for sessions that cannot safely continue on the current runner and have no runnable target account: log `session.exhausted`, notify user (Slack if enabled), preserve the logical session, and stop automatic retrying. User recovers via `aisup failover --to <account>` (switches to a now-eligible account, preserving the logical session) or `aisup stop` followed by `aisup start` (discards preserved session, starts fresh). `aisup start` must not discard `EXHAUSTED` state unless the user first runs `aisup stop`. Soft-threshold "no better alternate" deferrals while the current runner is still usable are not `EXHAUSTED`. Automatic recovery from EXHAUSTED (polling for cooldown expiry, auto-resume) is Phase 2.

### Out of Scope

- Permission fallback broker (Phase 2)
- Cost/token tracking (Phase 2)
- Supervisor-owned statusline hook installation (Phase 2 — when custom telemetry fields needed)
- Automatic EXHAUSTED recovery — polling for cooldown/rate-limit reset (Phase 2)
- Full reactive recovery — auth failure, network retry (Phase 2)
- Validation gate engine (Phase 2)
- Multi-LLM worker orchestration (Phase 3)
- Mobile dashboard (Phase 4)
- launchd auto-start
- Windows/Linux support

## Approach

**Chosen:** Modular monolith — single TypeScript project with clean internal module boundaries. Each feature (daemon, session, accounts, slack, journal, cli) is a separate module directory with explicit exports. No separate packages or workspaces — just clean imports.

**Why:** Simplest build setup for a new project. Module boundaries enforce separation without npm workspace overhead. Easy to extract packages later if needed.

**Alternatives considered:**
- npm workspaces (monorepo with `packages/`): overkill for a single-binary tool at this stage
- Separate CLI + daemon repos: unnecessary complexity, shared types are needed

## Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| tmux capture-pane escape code artifacts | Medium | Medium | Integration test spike in Task 3 validates capture-pane output fidelity. Strip ANSI escape codes before regex matching in monitoring loops. |
| Rate-limit output string format changes | Low | Medium | Use multiple regex patterns, make configurable. Fall back to statusline tap data. |
| Slack Socket Mode connection drops | Medium | Low | @slack/bolt handles reconnection automatically. Add connection status to event journal. |
| tmux session naming collision | Low | Low | Use UUID-based session names: `aisup-<first8chars-of-session-id>`. |
| Resume after switch loses /spec context | Medium | High | Inject continuation prompt with active skill + plan file path. Test with real /spec session (integration test). |
| Pilot CLI changes --resume behavior | Low | High | Runner abstraction makes the resume flag configurable. Monitor Pilot changelog. |
| Slack relay leaks sensitive output to cloud | Medium | Medium | Private channels only, output truncation (4000 char), `aisup init` warns about cloud logging. |
| Local HTTP API accessed by malicious process | Low | High | Per-install bearer token in `~/.aisup/api-token`. Fastify validates on all routes. |
| Daemon restart loses session tracking | Medium | Medium | `rehydrateSessions()` on startup reconciles the union of persisted session state files and live tmux sessions, covering state-without-tmux and tmux-without-state cases. |
| capture-pane misses scrolled output | High | Medium | Use `pipe-pane -o` for continuous output logging. capture-pane only for `!status` snapshots. |
| Shell injection via config paths | Low | High | Runner command built as structured args, then POSIX single-quote escaped at the tmux `send-keys` boundary via `singleQuote()`. Config loader validates paths for existence, absoluteness, no NUL bytes, no newlines — does NOT reject shell metacharacters (spaces, `$`, parentheses are valid in paths and handled by `singleQuote()`). Account names restricted to `[a-zA-Z0-9_-]`. tmux `send-keys -l` uses literal mode for user input. **tmux CLI calling convention:** ALL tmux commands MUST use `child_process.execFileSync('tmux', [...args])` or `child_process.spawn('tmux', [...args])` with NO `shell` option (defaults to `false`). Never use `execSync("tmux ...")` or template strings with shell interpolation. Only two boundaries cross a shell: (a) `pipe-pane -o` command argument (inner shell string, escaped with `singleQuote()`), (b) `send-keys -l` payload for `exec <runner_command>` (escaped with `singleQuote()`). The `tmux.ts` wrapper module enforces this — all callers go through the wrapper. |
| Stale telemetry causes wrong account/session decisions | Medium | High | Account scoring may use historical account telemetry with freshness penalties; active-session identity hydration uses launch time + account + cwd/project-slug matching and rejects stale/unrelated files. |
| Runtime files world-readable via umask | Medium | High | `~/.aisup/` mode 0700, token/state/log files mode 0600. Tests verify permissions. |
| Output log grows unbounded | Medium | Medium | Rotate at 50MB (configurable), retain 7 days (configurable). |
| Mid-turn failover corrupts session | Medium | High | Soft threshold (85%): SWITCH_PENDING_AT_IDLE, wait for idle. Hard threshold/429: interrupt first (Ctrl+C), then switch. |
| Abrupt kill-session loses transcript | Medium | High | Canonical `stopSession()` used by `aisup stop` and `!stop`; failover uses switch-owned `terminateRunnerForSwitch()` with the same graceful shutdown mechanics and transaction state. `destroySession()` is internal cleanup only. |

- Schema: `{ts: ISO8601, event_type: string, aisup_session_id?: string, claude_session_id?: string, account?: string, details: object, tokens?: number, cost_usd?: number}`
- **Schema presence rules:** Session-scoped events require `aisup_session_id` (`session.*`, `rate_limit.*`, `failover.*` for an existing session, `runner.*`, `migration.*`, `skill.*`, `output_log.*`, session-specific telemetry mismatches). Daemon-global events (`daemon.started`, `daemon.stopped`, `daemon.ready`) omit both session fields. Daemon/account-scoped telemetry/account events may omit `aisup_session_id` when they are not tied to an active session. `claude_session_id` included when available (null before telemetry hydration). `account` included for account-scoped operations.
- Writer: `appendEvent(event)` — JSON.stringify + newline + fs.appendFile (atomic enough for single-writer). Catch `ENOSPC` (disk full) — log to stderr and continue without crashing the daemon. Journal writes are best-effort, never fatal.
- Secret rejection: before writing, **recursively scan all keys** in the `details` tree for names matching `token`, `secret`, `apiKey`, or `authorization` (case-insensitive). Throw a validation error — secrets must never land in the journal file. The scan is recursive (not just top-level) to catch nested payloads like `details.response.authorization`.
- Reader: `readEvents(opts: {since?, type?, limit?})` — stream JSONL, filter, return array. Handle partial last line gracefully: if the final line doesn't parse as valid JSON, skip it (in-progress concurrent write). Only relevant during concurrent reads while daemon is appending.
- Create `~/.aisup/` directory on first write if missing

- `aisup start --cwd <path> [--plan <path>] [--dry-run]`: cwd precedence: (1) `--cwd <path>` if provided, (2) caller's `process.cwd()` when omitted. Passed to daemon via POST body. Reject `CREATING`, `ACTIVE`, `SWITCH_PENDING_AT_IDLE`, `SWITCHING`, and `STOPPING` with HTTP 409 and "Session operation in progress or already active. Recovery options: `aisup failover --to <account>` to resume with a specific account, or `aisup stop` then `aisup start` to start fresh." - PID file at `~/.aisup/daemon.pid` as JSON: `{ pid: number, port: number, startedAt: ISO8601 }`. Written atomically (write temp + rename). If no response or mismatched PID → stale (PID reuse), replace with warning. `daemon stop` uses the same validation — only sends SIGTERM after confirming the process is an aisup daemon via health check.

All other API routes return HTTP 503 with body `{"error": "daemon_starting", "message": "Daemon is starting. Retry shortly."}` while readiness state is not READY. Daemon is READY only after: config loaded, journal initialized, account registry initialized, HTTP server listening, sessions rehydrated through state/tmux union reconciliation (including pipe-pane restoration checks, state-without-tmux recovery, and tmux-without-state orphan detection), monitoring loops registered. **CLI behavior on 503:** CLI retries 503 responses up to 3 times with 1s delay for startup commands (`start`, `failover`). Non-startup commands (`status`, `log`) fail immediately with "Daemon starting, retry shortly."
- **Daemon logging:** Use an internal rotating logger (e.g., `pino` with file transport, or a simple `fs.createWriteStream` with periodic reopen). Do NOT redirect stdout/stderr via shell redirection — naive rename-based rotation doesn't work with open file descriptors (the process continues writing to the renamed file). Internal logger rotates at `daemon.log_max_size_mb` (default 10MB), retains 1 previous log. Alternative: copy-truncate (copy → truncate to 0 bytes, FD stays valid).

### Task 3: Session Controller (tmux)

**Objective:** Manage tmux sessions for CLI process lifecycle. Handle creation, attachment, detachment, destruction, input via send-keys, and output monitoring via capture-pane.

**Dependencies:** Task 1 (config), Task 2 (journal for logging session events)

**Files:**

- Create: `src/session/tmux.ts` — tmux session create/destroy/list/attach/send-keys/capture-pane
- Create: `src/session/manager.ts` — session lifecycle (create, attach, stop, get state)
- Create: `src/session/types.ts` — SessionState enum, SessionInfo type
- Create: `tests/fixtures/fake-runner.sh` — deterministic test fixture (echoes input, accepts commands, exits on "quit")
- Test: `tests/session/tmux.test.ts`
- Test: `tests/session/manager.test.ts`

**Key Decisions / Notes:**

- **Design Decision: tmux-native sessions (no node-pty wrapper).** The runner command runs directly inside a tmux session. Rationale: (1) Session persistence across daemon crashes/restarts (critical for long-running sessions — tmux provides this for free), (2) User can attach/detach via `aisup attach` or manual `tmux attach-session`, (3) Simpler architecture — no intermediate PTY abstraction. Trade-off vs PRD's mention of node-pty: node-pty would tie PTY lifecycle to the daemon process, meaning daemon crash = session loss. Window resize is handled by tmux natively — when a user resizes their terminal after `aisup attach`, tmux sends SIGWINCH to the runner process automatically. No programmatic window-size passing via daemon or HTTP API needed.
- **Four-step launch sequence (guarantees zero output loss + reliable crash detection):**
  1. `tmux new-session -d -s <name> -c <cwd> -e ${config.runner.config_dir_env}=<dir> /bin/sh` — creates session with controlled `/bin/sh` shell (bypasses user dotfiles entirely — no .zshrc/.bashrc sourced, no PATH alteration, no prompt output). `/bin/sh` is POSIX-guaranteed, starts instantly, and accepts the subsequent `exec` command predictably. User's default interactive shell and dotfiles are never part of runner launch semantics.
  2. `tmux set-window-option -t <name> remain-on-exit on` — ensures dead pane persists after process exit so `#{pane_dead}` can be read. Use `set-window-option` (not `set-option -t`) — it's the semantically correct command for window-scoped options like `remain-on-exit`.
  3. `tmux pipe-pane -o -t <name> 'cat >> ${singleQuote(logPath)}'` — attach output capture BEFORE any runner output. Ensure parent directory exists before calling. Log path is shell-escaped via `singleQuote()`.
  4. **Two separate send-keys calls** (the `-l` flag makes ALL subsequent arguments literal — a trailing `Enter` would be sent as the text "Enter", not a keypress):
     - `tmux send-keys -l -t <name> -- 'exec <escaped_command>'` — sends the command text literally. The `<escaped_command>` uses the absolute path resolved by `validateRunner()` — no PATH dependency in the tmux shell.
     - `tmux send-keys -t <name> Enter` — sends the Enter keypress to execute
     `exec` replaces the shell with the runner process. When the runner exits, the pane process is dead and `#{pane_dead}` = 1. Without `exec`, the shell survives runner exit and `#{pane_dead}` stays 0 (shell still alive).
  This eliminates the race between session creation and pipe-pane attachment, and ensures reliable crash detection. Zero-output-loss guarantee refers to runner output — `/bin/sh` emits no startup output.
- **Output monitoring: dual approach.**
  - `tmux pipe-pane -o -t <name> 'cat >> <log_path>'` — continuous raw output stream to `~/.aisup/sessions/<aisup_session_id>/output.log`. Used by monitoring loops for regex matching (429 detection, skill detection). Captures ALL output, not just visible pane.
  - `tmux capture-pane -p -t <name>` — point-in-time visible pane snapshot. Used only for `!status` command and prompt detection.
- **Output log rotation:** Rotate when file exceeds `output_log_max_size_mb` (default 50MB). Rotation sequence: (1) `tmux pipe-pane -t <name>` (stops current pipe), (2) rename `output.log` → `output.log.1`, (3) `tmux pipe-pane -o -t <name> 'cat >> <new_log_path>'` (restart pipe to new file), (4) emit `output_log.rotated` journal event, (5) reset ALL output scanners (recovery handler, skill detector, Slack relay) to offset 0 on the new file. Brief output gap during rotation is acceptable at 50MB threshold. Retain logs for `output_log_retention_days` (default 7). Cleanup on daemon tick.
- **Output cursor model:** All output scanners track `{path, offset, generation}`. Generation increments on rotation. On rotation, scanners reset to offset 0 of new file. Prevents stale-offset reads after file rename.
- **Session state atomicity:** Session state files (`~/.aisup/sessions/<id>/state.json`) use atomic write: `writeFileSync(path + '.tmp', data)` → `renameSync(path + '.tmp', path)`. Same pattern as statusline tap.
- **Input: `tmux send-keys -l`** for all literal text (user messages, `!cmd` relay). The `-l` flag prevents tmux from interpreting key names (e.g., the text "Enter" would be sent as literal characters, not a keypress). Use named keys (`Enter`, `C-c`) separately for control actions only.
- **Crash detection:** `tmux display-message -p -t <name> '#{pane_dead}'` returns "1" when process has exited. `#{pane_dead_status}` gives exit code. Requires both `remain-on-exit on` (step 2) and `exec` (step 4). Do NOT rely on `tmux has-session` for crash detection — it returns true even when the pane process is dead (because `remain-on-exit on` keeps the session alive). Dead panes are cleaned up explicitly by the recovery handler or graceful stop after reading exit status via `tmux kill-session`. For switch transactions, also read and persist tmux `#{session_id}` and pane ID (`#{pane_id}`) for the source and every target attempt so crash recovery can distinguish a stale dead source session from a created target with the same tmux name.
- tmux session naming: `aisup-<first8chars-of-aisup_session_id>` to avoid collision
- **Session states (SessionState enum):** CREATING → ACTIVE → SWITCH_PENDING_AT_IDLE → SWITCHING. `SWITCHING` resolves to ACTIVE on success, remains SWITCHING during bounded retry/recoverable in-progress work, or becomes EXHAUSTED when no runnable target remains after source termination or hard/429/source-dead recovery cannot continue. Also: STOPPING (during graceful stop), STOPPED (terminal and the only state that permits a fresh `aisup start` when no live tmux session remains), EXHAUSTED (recoverable/manual, not entered for soft-threshold no-target/no-better-target deferrals while the current runner is still usable). All states except reusable `STOPPED` reserve the MVP single-session slot.
- **State/loop processing matrix (which loops process which states):**
  | State | Rate-limit monitor | Recovery handler | Health monitor |
  |---|---|---|---|
  | ACTIVE | Score + threshold check | Crash/429 detection | Heartbeat |
  | SWITCH_PENDING_AT_IDLE | Idle check → trigger `performSwitch()` | Crash → upgrade to immediate switch | Skip |
  | CREATING | Skip | Skip | Skip |
  | STOPPING | Skip | Skip | Skip |
  | SWITCHING | Skip | Skip | Skip |
  | STOPPED | Skip | Skip | Skip |
  | EXHAUSTED | Skip | Skip | Skip |
  Globally skipped states (CREATING, STOPPING, SWITCHING, STOPPED, EXHAUSTED) indicate the session is already being managed by another operation. `SWITCH_PENDING_AT_IDLE` is a special case: the rate-limit monitor must check idle condition, and recovery must detect crashes that occur while waiting for idle (upgrading to immediate switch rather than ignoring).
- **Account states (AccountState enum — separate from session states):** HEALTHY → DEGRADED (soft limit) → UNAVAILABLE (hard limit/auth/circuit breaker) → COOLDOWN → HEALTHY. EXHAUSTED is NOT an account state — it's a session state meaning "all accounts unavailable."
- `tmux.ts` wraps tmux CLI commands using `execFileSync('tmux', [...args])` — never shell strings. Commands: `new-session -d -s <name> -c <cwd> -e KEY=VAL /bin/sh`, `set-window-option -t <name> remain-on-exit on`, `send-keys -l`, `capture-pane -p -t <name>`, `pipe-pane -o -t <name>`, `kill-session -t <name>`, `display-message -p -t <name> '#{pane_dead}'`, `display-message -p -t <name> '#{pane_dead_status}'`, `display-message -p -t <name> '#{pane_pipe}'`, `respawn-pane -k -t <name> -c <cwd> -e KEY=VAL /bin/sh`
- **Canonical restart primitive (used by `restartSession()` and switch recovery):** Dead panes cannot accept `send-keys`. Restart sequence: (1) Read `#{pane_dead_status}` for journal/diagnostics, (2) stop pipe-pane: `tmux pipe-pane -t <name>`, (3) respawn: `tmux respawn-pane -k -t <name> -c <cwd> -e ${config.runner.config_dir_env}=<dir> /bin/sh` — kills dead pane and starts fresh `/bin/sh`, (4) re-apply: `tmux set-window-option -t <name> remain-on-exit on`, (5) restart pipe-pane: `tmux pipe-pane -o -t <name> 'cat >> ${singleQuote(logPath)}'`, (6) send exec command (same two-step send-keys as initial launch). Requires tmux ≥ 3.0 for `-e` on `respawn-pane`. Doctor validates tmux version.
- **`terminateRunnerForSwitch(name)`:** Internal helper that executes the same Ctrl+C → wait 2s → /exit → poll `#{pane_dead}` 5s → force kill-session process-shutdown mechanics as `stopSession()`, but: (a) does NOT change session state (caller has already set SWITCHING), (b) does NOT emit `session.stop`, (c) updates `switch_tx.phase = "stopping"` and records `phase_timestamps.stopping`. After the source pane is dead, it must enter a durable `source_destroyed`/`stopping_cleanup` phase, run idempotent `tmux kill-session -t <source_tmux_name>`, verify `tmux has-session` is false for the source, persist that source destruction completed, and only then allow migration or target creation. Used exclusively by the switcher.
- **Test isolation:** All tmux tests use a dedicated socket: `tmux -L aisup-test`. This avoids interfering with the user's tmux server. Cleanup in `afterEach`: `tmux -L aisup-test kill-server`.
- `fake-runner.sh` test fixture: simple bash script that echoes stdin, prints a prompt `> `, and exits on `quit` command. Used for all session controller tests — no dependency on real Pilot/Claude.
- **Integration test spike (do first):** Before building the full session manager, write a minimal integration test that spawns a tmux session (on test socket) running `fake-runner.sh`, sends input via `send-keys -l`, captures output via `capture-pane` AND reads from `pipe-pane` log file, and verifies round-trip works. Spike must also prove: launch succeeds when user's default shell is zsh/fish with custom prompts (because we bypass it with `/bin/sh`), and launch succeeds when daemon PATH differs from tmux server PATH (because we use absolute executable path).

**Definition of Done:**

- [x] `createSession(name, command, args, env, cwd)` creates a tmux session using four-step launch (idle shell → set-window-option remain-on-exit on → pipe-pane → exec command)

### Task 5: Account Registry and Scoring

**Objective:** Manage multiple Claude account configurations, read usage data from statusline tap files, score accounts by remaining headroom, and implement circuit breaker logic.

**Dependencies:** Task 1 (config for account definitions)

**Files:**

- Create: `src/accounts/registry.ts` — account CRUD, health state machine
- Create: `src/accounts/scorer.ts` — read statusline tap files, score by headroom
- Create: `src/accounts/circuit-breaker.ts` — failure counting, cooldown, state transitions
- Create: `src/accounts/types.ts` — AccountState enum, AccountInfo type
- Test: `tests/accounts/scorer.test.ts`
- Test: `tests/accounts/circuit-breaker.test.ts`

**Key Decisions / Notes:**

- Account states: HEALTHY → DEGRADED (soft limit) → UNAVAILABLE (hard limit/auth/circuit breaker) → COOLDOWN → HEALTHY
- **Telemetry-driven account state transitions (evaluated by health checker loop each tick):**
  - `five_hour_used_pct ≥ soft_pct` OR `seven_day_used_pct ≥ soft_pct` → DEGRADED
  - `five_hour_used_pct ≥ hard_pct` OR `seven_day_used_pct ≥ hard_pct` OR active 429 detected in output → UNAVAILABLE
  - Both rate-limit windows are enforced independently. The blocking window (whichever is closer to its cap) drives the state transition. Cooldown ETA uses the `resets_at` of the blocking window (the one that caused UNAVAILABLE).
  - Circuit breaker trips (3 consecutive failures) → UNAVAILABLE, then COOLDOWN after `cooldown_seconds`
  - `resets_at` timestamp passes AND no active failures → reset to HEALTHY
  - Account with `enabled: false` in config → skipped by scorer, reported as informational in `aisup doctor`
- **Two-tier scoring:**
  - **Fresh telemetry available:** Score = `(100 - five_hour_used_pct) * 0.7 + (100 - seven_day_used_pct) * 0.3`. Higher = better. Account scoring telemetry is matched by `transcript_path` prefix: `transcriptPath.startsWith(path.resolve(account.config_dir) + '/')`. The trailing `/` is mandatory to prevent `.claude` from matching `.claude-account2`. All `config_dir` values must be resolved to absolute paths before matching. Example: path `/Users/alec/.claude/projects/-Users-alec-Projects-foo/abc.jsonl` → matches account with `config_dir: ~/.claude` (resolved to `/Users/alec/.claude`). This account-scoring telemetry may be historical and must never hydrate an active session's `claude_session_id` or `transcript_path`; active-session identity uses `readTelemetryForActiveSession(session)`.
  - **No fresh telemetry (inactive account):** Fall back to `accounts[].priority` from config (integer, lower = preferred). Do NOT pretend unknown headroom is 50% — that's a guess. Priority-based selection is explicit and predictable. **Before priority fallback, filter to only HEALTHY or DEGRADED accounts.** If all accounts are UNAVAILABLE, COOLDOWN, disabled, or excluded from selection, return `null`. `selectBestAccount()` returning null means no eligible account exists for that selector call; the caller decides whether to defer, retry another target, or set SESSION state to EXHAUSTED based on `SwitchReason`, source-runner liveness, and whether the current runner can safely continue. No account record ever has state EXHAUSTED.
- **Three telemetry states (clarified):**
  - **(a) No telemetry files exist** (account never used or files cleaned up) → priority-based fallback
  - **(b) Stale telemetry, `resets_at` in the past** → rate limit has reset, capacity unknown → priority-based fallback
  - **(c) Stale telemetry, `resets_at` in the future** → last known rate-limit data still relevant → apply score formula with a 0.8 confidence multiplier: `score * 0.8`. This penalizes stale data without ignoring it — a 94% usage account scores `6 * 0.8 = 4.8` instead of 6, still lower than a fresh 50% account scoring 50. Do NOT ignore stale-future data entirely.
- Circuit breaker: after `max_failures` consecutive failures on an account, mark UNAVAILABLE for `cooldown_seconds`. Timer-based reset.
- Circuit breaker state persisted to `~/.aisup/circuit-breaker-state.json` on every state change. Restored on daemon startup. Format: `{[accountName]: {failures: number, state: string, unavailableSince?: ISO8601}}`. Stale entries (older than `cooldown_seconds`) reset to HEALTHY on load.
- `selectBestAccount(exclude?: string[])` → returns highest-scoring eligible account (HEALTHY or DEGRADED), or null if all UNAVAILABLE/COOLDOWN. **Eligibility:** HEALTHY and DEGRADED are eligible for selection. UNAVAILABLE and COOLDOWN are never eligible. **Tie-break order:** score (higher wins) → configured `priority` (lower wins) → account name (alphabetical). Deterministic selection.
- `selectSwitchTarget(reason, currentAccount, excludedAccounts)` wraps `selectBestAccount()` for failover. Soft-threshold callers require a target that is strictly better than the current account for the triggered rate-limit window or weighted score; hard-threshold, 429, source-dead, and post-source-termination recovery callers do not require that improvement because the current runner cannot safely continue.

If idle condition is met, it rechecks target suitability; if no better target remains, clears pending state back to `ACTIVE`, emits throttled nonterminal no-target event, and keeps monitoring. If a better target remains, it triggers `performSwitch()`. No separate watcher needed — the same loop that set the state also executes it.
  - **Hard threshold (95%) or 429 detection:** Triggered when EITHER window ≥ 95%. Immediate switch — interrupt with Ctrl+C first (via graceful stop sequence), then switch.
  - When recording threshold breach, emit `rate_limit.threshold_crossed`, include `triggered_window: "five_hour" | "seven_day"` in the event details, include both window percentages and thresholds, and use that window's `resets_at` for cooldown ETA.
  - This prevents killing a session mid-turn, which would lose in-progress work and corrupt transcript state.
- Recovery handler: **Two-phase crash detection:** (1) Check `tmux has-session -t <name>` first. If session gone (exit code non-zero), treat as crash with unknown exit code — log `session.destroyed_externally` event and trigger recovery. (2) If session exists, check `#{pane_dead}` — returns "1" when runner has exited. This covers both dead-pane (remain-on-exit) and externally-destroyed scenarios. Reads `pipe-pane` output log file for 429 regex patterns (NOT `capture-pane` — that only shows visible pane). Patterns: `/rate limit/i`, `/Too many requests/i`, `/429/`, `/usage cap/i`, `/wait.*minutes/i`. **Apply `stripAnsi()` (from `strip-ansi` package) to pipe-pane output content before ALL regex matching** — raw output contains heavy ANSI escape codes that interfere with pattern matching.
- **Recovery decision matrix:**
  | Condition | Action | Counter |
  |---|---|---|
  | Crash without 429 in recent output | `restartSession()` on same account | Increment same-account restart counter |
  | Same-account restart counter ≥ 3 within 5 min | Escalate to `selectSwitchTarget(reason: "restart_failures", current, excluded)` | Reset restart counter, increment circuit breaker |
  | Crash with 429 in recent output | `selectSwitchTarget(reason: "429", current, excluded)` | Increment circuit breaker |
  | Circuit breaker tripped (3 rate-limit failures) | `selectSwitchTarget(reason: "circuit_breaker", current, excluded)` | N/A — account marked UNAVAILABLE |
  `restartSession()` reuses the current account: does NOT call `selectBestAccount()`. Uses the canonical restart primitive (respawn-pane — see Task 3) since the pane is dead after crash. **Launch decision:** if `claude_session_id` is non-null AND transcript file exists in current account's config dir → `buildResumeCommand()`. Otherwise → `buildLaunchCommand()` (fresh start), record `launch_mode: "fresh"` and reason (`recovery.restart_fresh_no_session_id`) in journal event. On successful restart, reset same-account restart counter. Repeated restart failures that escalate to account switch use the same bounded target-attempt policy as `performSwitch()`: exclude current plus tried targets, clean up failed target sessions, and enter recoverable `EXHAUSTED` only after no runnable target remains. Two distinct counters: same-account restart counter (process crashes) and circuit breaker failure counter (rate-limit switches). This prevents ordinary process crashes (OOM, node crash, user kill) from unnecessarily burning account switches.
- **Output log byte offset tracking:** Recovery handler maintains `{path, offset, generation}` per session. Each tick reads only new bytes from `pipe-pane` output log (from offset to EOF). **Daemon restart cursor initialization:** On rehydration of a LIVE pane (runner still running): initialize offset to current file size (EOF) — skip historical output, only scan new output going forward. On rehydration of a DEAD pane (runner crashed while daemon was down): scan last 64KB of output log for 429 patterns to classify crash cause before initiating recovery, then move to EOF. **Log rotation reset:** After rotation (see Task 3 output cursor model), all scanners reset to offset 0 with incremented generation. This prevents stale-offset reads and ensures 429 detection, skill detection, and Slack relay remain functional after rotation.
- **Session state filtering:** Each loop processes only the states listed in its column of the state/loop matrix (Task 3, Key Decisions) after rehydration has registered persisted non-terminal sessions, including persisted sessions whose tmux session is missing. The globally-skipped states (CREATING, SWITCHING, STOPPING, STOPPED, EXHAUSTED) indicate the session is already being managed by another operation. Soft-threshold no-suitable-target deferrals remain in monitored `ACTIVE`/`SWITCH_PENDING_AT_IDLE` paths and must not be represented as `EXHAUSTED`. `SWITCH_PENDING_AT_IDLE` is processed by the rate-limit monitor (idle check) and recovery handler (crash escalation) but skipped by health monitor.
- **`claude_session_id` hydration:** The `claude_session_id` field in session state is initially null at launch. It is populated only by `readTelemetryForActiveSession(session)`, which matches candidates by launch time, current account config dir, and resolved cwd/project slug. If `claude_session_id` is already known, validate exact `statusline-<id>.json` against current account/cwd before accepting it. Rejected candidates emit `telemetry.session_mismatch`. Do not hydrate from `readTelemetryForAccount()`. All code that needs `claude_session_id` (e.g., `--resume` flag, transcript path lookup) must handle the null case.
- **tmux command timeouts:** All `tmux` command executions (send-keys, capture-pane, has-session, etc.) use a 5s timeout via `child_process.execFileSync`/`spawn` timeout option (no shell). If tmux hangs (e.g., broken socket), the command fails with a timeout error rather than blocking the daemon event loop indefinitely.
