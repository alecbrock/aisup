## Decisions Made in Phase 1 (Critical for Phase 2)

### Architecture

- **Decision:** tmux-native sessions (no node-pty wrapper)
  **Rationale:** Sessions survive daemon crashes — tmux provides persistence for free. User can attach/detach via `aisup attach` or manual `tmux attach-session`. node-pty ties PTY lifecycle to daemon process, meaning daemon crash = session loss.
  **Impact on Phase 2:** Multi-session support (Phase 2) adds tmux sessions, not node-pty processes. Window resize handled by tmux natively. Worker orchestration (Phase 3) should use the same tmux-native model.
  **PRD divergence:** PRD mentions "node-pty" — Phase 1 implementation uses tmux-native. PRD should be updated.

- **Decision:** Four-step launch sequence (idle /bin/sh → remain-on-exit → pipe-pane → exec command)
  **Rationale:** Guarantees zero output loss and reliable crash detection. `/bin/sh` bypasses user dotfiles. `exec` ensures `#{pane_dead}` returns 1 after runner exit. Pipe-pane attached before any runner output.
  **Impact on Phase 2:** Any new session types (workers, multi-session) must use this same sequence.

- **Decision:** `CLAUDE_CONFIG_DIR` evaluated at process start — account switching requires process restart
  **Rationale:** This is a Claude/Pilot constraint. The env var is set in the tmux session environment.
  **Impact on Phase 2:** Cannot do in-process account switching. Switch always means kill + restart.

### Session Identity Model

- **Decision:** Two distinct IDs — `aisup_session_id` (stable UUID, supervisor-generated) and `claude_session_id` (discovered from statusline telemetry, used for `--resume`)
  **Rationale:** `aisup_session_id` is stable across failover. `claude_session_id` changes when a fresh start is needed.
  **Impact on Phase 2:** Multi-session support must use `aisup_session_id` for all internal state (tmux name, state directory, Slack channel, output log). `claude_session_id` is per-runner-instance.

### Single-Session MVP

- **Decision:** One active session at a time. `aisup start` rejected for all non-terminal states.
  **Rationale:** Simplifies admission logic and avoids session ID args on every CLI command.
  **Impact on Phase 2:** Multi-session requires: session ID args on CLI commands, session picker, per-session state isolation (already in `~/.aisup/sessions/<id>/`), per-session Slack channels (already keyed by `aisup_session_id`), and session-scoped monitoring loops. `daemon.default_cwd` was removed from MVP config — re-evaluate for multi-session where sessions may be started programmatically.

### EXHAUSTED State

- **Decision:** EXHAUSTED is a session state (not account state). Preserves logical session. Manual recovery via `aisup failover --to <account>` or discard via `aisup stop` + `aisup start`.
  **Rationale:** Avoids crash loops when all accounts are rate-limited. Operator decides when to retry.
  **Impact on Phase 2:** Automatic EXHAUSTED recovery needs: polling for cooldown/rate-limit reset, auto-resume when earliest `resets_at` passes. Must respect the `EXHAUSTED` → `SWITCHING` → `ACTIVE` transition. Do NOT change `EXHAUSTED` to auto-resume without a config toggle — some operators prefer manual control.

### Soft-Threshold Deferrals

- **Decision:** Soft-threshold with no better target keeps session ACTIVE and continues monitoring. Does NOT enter EXHAUSTED.
  **Rationale:** EXHAUSTED should only be entered when the current runner cannot safely continue. Soft-threshold means the account is degraded but still usable.
  **Impact on Phase 2:** Automatic EXHAUSTED recovery logic must not trigger for soft-threshold deferrals — they're already being monitored.

### Statusline Store — No Hook Installation

- **Decision:** MVP reads existing tap files from `/tmp/pilot-failover/`. Does NOT install or modify Claude/Pilot statusline hooks.
  **Rationale:** Avoids coupling to Claude's internal settings structure. Existing tap script already writes the needed telemetry.
  **Impact on Phase 2:** Supervisor-owned hook installation is Phase 2 — needed when custom telemetry fields are required (e.g., cost tracking, extended model info). Must modify `<config_dir>/settings.json` to set `statusLine.command`.

### Resume Prompt Mode

- **Decision:** `resume_prompt_mode: never` (default). `pilot --resume` already preserves full conversation context. Auto-injecting a prompt risks starting an unwanted turn.
  **Rationale:** Validated that `--resume` alone is sufficient for session continuity.
  **Impact on Phase 2:** Two deferred modes: `manual` (user triggers via `!inject` Slack command) and `auto_after_prompt` (wait for prompt indicator in capture-pane). Both require prompt detection logic not yet built. The `buildContinuationPrompt()` function in `src/skills/continuation.ts` is ready to use.

### Daemon Loop Wiring

- **Decision:** Loops are class-based with `start()/stop()/tick()`. Tick logic is placeholder — callback receives threshold results but actual telemetry polling is not wired in daemon/index.ts.
  **Rationale:** Each loop is independently unit-testable. Daemon integration wires the real telemetry reads and session state checks.
  **Impact on Phase 2:** Full daemon integration must wire: rate-limit monitor reads `readTelemetryForActiveSession()` per tick, recovery handler reads pipe-pane output log per tick, health checker reads account config dirs per tick, idle watchdog reads output log mtime per tick. The loop-manager.ts `startAll()/stopAll()` is ready. The state/loop processing matrix (which loops process which states) is defined in the plan's Task 3 section.

### API Stubs

- **Decision:** Several daemon API endpoints return stubs (POST/DELETE `/api/sessions`, POST `/api/failover`).
  **Rationale:** CLI commands for start/stop/failover call these endpoints, but the real session creation/switching logic is in SessionManager and Switcher modules. The API routes need to call these modules.
  **Impact on Phase 2:** Before Phase 2 can build on top of the API, these stubs must be wired to real implementations. The CLI already handles the HTTP client side correctly.

## Deviations from Plan

- **Daemon loop tick wiring:** Plan says Task 8 creates loops and Task 12 wires them into daemon startup. Implementation created the loop classes with testable static methods (e.g., `RateLimitMonitor.checkThresholds()`) but daemon tick callbacks are placeholders. The `LoopManager.startAll()` is called but individual tick functions don't poll real telemetry yet.
- **Daemon API routes:** Plan's Task 12 says "wire all modules together." API routes for sessions/failover are stubs returning placeholder responses. The admission predicate (`canStartNewSession`) is fully implemented and tested.
- **Session rehydration:** Basic implementation added — reconciles persisted state files with live tmux sessions. Does not yet implement full switch_tx recovery, pipe-pane restoration checks, or the complete recovery decision matrix for state-without-tmux scenarios.
- **`terminateRunnerForSwitch()`:** Function signature and concept defined in session types, but the full implementation (preserving SWITCHING state, not emitting session.stop, updating switch_tx.phase) is not wired. `stopSession()` handles the basic graceful stop mechanics.
- **`performSwitch()` full 10-step sequence:** The individual components exist (migrator, switcher validation, session manager, runner builder) but the orchestrating `performSwitch()` function that chains all 10 steps with switch_tx transaction safety is not implemented as a single callable function.
