## MUST FIX

#1 — Single-session enforcement misses in-flight session states
- Issue: The plan’s one-session invariant is stricter than the `aisup start` guard. It only rejects existing sessions in `ACTIVE` or `SWITCHING`, while the canonical state machine also has `CREATING`, `SWITCH_PENDING_AT_IDLE`, `STOPPING`, and `EXHAUSTED` as non-terminal/in-flight or recoverable states. `SWITCH_PENDING_AT_IDLE` is explicitly still supervised, `CREATING` and `STOPPING` are operation-owned transitions, and `EXHAUSTED` preserves a logical session for manual recovery.
- Impact: A second `aisup start` can race session creation, pending failover, or graceful stop, creating two tmux sessions/state directories despite MVP single-session scope. It can also let a user bypass the EXHAUSTED preservation path or break failover recovery by replacing state while an operation-owned state is still active.
- Fix: Define one canonical start-admission predicate and propagate it everywhere: `aisup start` is allowed only when no session state exists or the only persisted session is terminal `STOPPED` and has no live tmux session. Reject `CREATING`, `ACTIVE`, `SWITCH_PENDING_AT_IDLE`, `SWITCHING`, and `STOPPING` with 409 “session operation in progress/already active”; reject `EXHAUSTED` with the existing recovery-specific message. If `STOPPED` exists but tmux still has a live `aisup-*` session, treat it as inconsistent/orphaned and require `aisup stop --force` or doctor recovery before starting.

#2 — Switch launch failure can strand a logical session
- Issue: The switch path has durable recovery for daemon crashes during `creating`/`resuming`, but not for ordinary target launch/resume failures while the daemon remains alive. The state enum still says `SWITCHING → ACTIVE (on success) | STOPPED (on failure)`, while Task 7 kills the source runner before creating/resuming the target. There is no bounded retry policy, no “tried targets” record, no cleanup contract for partially created failed target tmux sessions, and no final preserved recovery state for a failed target launch.
- Impact: A bad target account, broken runner invocation, auth/config failure, or `respawn-pane` failure can kill the source session and then mark the logical session `STOPPED` or leave it stuck in `SWITCHING`. A partial failed target can also block retries because the stable tmux name is already occupied. That breaks the core failover promise: the transcript may be preserved, but the operator loses a clear recovery path and monitoring/CLI status can report the wrong lifecycle state.
- Fix: Make `SWITCHING` failure semantics transaction-safe. Add `switch_tx.attempts[]` with `{target_account, phase, target_tmux_session_id?, target_pane_id?, error_summary, ts, cleaned_up}` plus `tried_accounts` and `last_launch_error`. On target create/resume failure, emit `runner.launch_failed` or `runner.respawn_failed`, clean up any partially created target tmux session before the next attempt, mark/increment the failed target’s circuit breaker when appropriate, and for automatic failover select the next eligible account excluding current plus tried targets. Retry until one target succeeds or no target remains. If no target remains after source termination, set session state to `EXHAUSTED` (not `STOPPED`), preserve `aisup_session_id`, target-attempt metadata or a `last_switch_failure` snapshot, transcript paths, and Slack channel map, then notify the operator with manual recovery instructions. Manual failover launch/resume failures should return a typed non-200 response while preserving the same recoverable logical session.

#4 — Switch crash recovery can confuse the dead source session with the target
- Issue: The switcher reuses the same tmux name for source and target, but `switch_tx` only stores `source_tmux_name` and `target_tmux_name`, and the recovery table advances from `stopping` to `migrating` when `#{pane_dead}` is true without first proving the source tmux session was killed. If the daemon crashes after the source runner exits but before `kill-session` cleanup, the later `creating` recovery check (`tmux has-session -t <target_tmux_name>`) sees the leftover dead source session under the same name and incorrectly treats it as the created target.
- Impact: Crash recovery during failover can resume/restart the old source-side dead pane, launch under the wrong account environment, skip target creation, remain stuck in `SWITCHING`, or report a successful switch while the target account was never actually launched. That breaks the plan’s crash-safe failover guarantee and can corrupt account/session state after exactly the failure mode the transaction table is supposed to handle.
- Fix: Make source teardown and tmux identity disambiguation explicit in the transaction. Persist tmux object IDs, not only names: `source_tmux_session_id`, `source_pane_id`, and, after each target creation attempt, target tmux session/pane IDs on that attempt. Add a `source_destroyed` (or `stopping_cleanup`) switch phase between `stopping` and `migrating`. `terminateRunnerForSwitch()` and rehydration must, after the source pane is dead, always run idempotent `kill-session -t <source_tmux_name>` and verify `tmux has-session` is false before advancing to migration or target creation. In `creating`, an existing session named `target_tmux_name` may be accepted only if it matches the persisted target tmux ID for the current attempt; if it matches the stored source ID or has no target marker, treat it as stale source cleanup and kill/recreate, or fail recoverably. If the plan chooses a temporary target tmux name instead, it must define the rename/finalization step and preserve the stable `aisup_session_id`, state directory, Slack channel, and output-log prefix.

#5 — Soft-threshold target selection can exhaust or worsen live sessions
- Issue: Automatic failover always excludes the current account, and the guard says any automatic `selectBestAccount()` null result sets the session to `EXHAUSTED`. That is correct only when the current runner is already unusable or terminated. At the 85% soft threshold, the current account is merely `DEGRADED` and the runner is still live; if no alternate account is eligible, the plan would mark the logical session `EXHAUSTED`, skip all monitoring loops, and stop retrying even though the current session can continue. The same root issue also allows a soft-threshold switch to an eligible but worse DEGRADED target because `selectBestAccount(exclude: [current])` does not require the target to improve the triggered rate-limit window or overall score.
- Impact: A normal soft-limit condition with no better target can disable supervision for a still-running session or migrate from an 85–90% account to a 94% account that immediately hard-thresholds or exhausts. The daemon would no longer reliably detect a later hard cap, 429, crash, or newly eligible account, which breaks proactive failover and recovery exactly when account capacity is constrained.
- Fix: Distinguish nonterminal “no suitable alternate target yet” from terminal EXHAUSTED. For soft-threshold callers, precheck with a switch-reason-aware target selector that excludes the current account and requires a strictly better target for the triggered window or weighted score; if no suitable target exists, keep the session `ACTIVE`, emit `failover.no_target_available` with `terminal: false` and `reason: "soft_no_better_target"`, notify at a throttled cadence, and continue monitoring. If the session is already `SWITCH_PENDING_AT_IDLE` and the idle-time recheck finds no better target, clear the pending state back to `ACTIVE` with a `last_soft_no_target_at`/notification-throttle marker rather than entering EXHAUSTED. Only hard-threshold/429 paths, crash-escalation paths, or post-source-termination target exhaustion may enter `EXHAUSTED`. `selectBestAccount()` returning null must no longer globally imply session EXHAUSTED; the caller’s reason, source-runner liveness, and target-improvement requirement decide.

#6 — Session telemetry hydration can bind to a stale or unrelated Claude session
- Issue: The plan correctly rejects `statusline-latest.json`, but it never defines a session-specific telemetry resolver for the period before `claude_session_id` is known. `readTelemetryForAccount(configDir)` filters only by account config-dir prefix and returns the freshest file, while the rate-limit monitor later “populates” `claude_session_id` when it first reads telemetry containing `session_id`. On a machine with prior statusline files for the same account, the new supervised session can hydrate from an unrelated historical Claude session before the new runner emits its first statusline file. After failover, the known `statusline-<claude_session_id>.json` can also temporarily still point at the source account transcript until the resumed target writes fresh telemetry, and the plan does not require rejecting that stale source-side file.
- Impact: The daemon can attach the wrong `claude_session_id` and `transcript_path` to the logical `aisup_session_id`, causing failover to copy/resume the wrong transcript, rate-limit decisions to use another session’s usage, Gate 4 to pass falsely, and recovery/status output to report a conversation that is not actually supervised. This is a blocking identity/data-integrity failure because it corrupts the canonical mapping that all resume and migration logic depends on.
- Fix: Define a canonical `readTelemetryForActiveSession(session)` resolver that is separate from account scoring. Persist `session.cwd`, `current_account`, `launch_started_at`, and the expected Claude project slug or resolved cwd at session creation and each target launch attempt. If `session.claude_session_id` is known, read only `statusline-<id>.json` and accept it only when `session_id` matches, `transcript_path` is under the current account config dir, and `cwd` or `workspace.project_dir` matches the stored session cwd; otherwise keep prior telemetry, mark current telemetry pending/stale, and emit `telemetry.session_mismatch`. If `claude_session_id` is null, scan statusline files excluding symlinks/latest and accept only candidates with mtime at or after `launch_started_at` (with a small clock-skew tolerance), transcript prefix under the current account config dir, and cwd/project-slug matching the stored session cwd. Do not hydrate from `readTelemetryForAccount()`. Until a matching candidate exists, keep `claude_session_id`/`transcript_path` null and skip statusline-based rate-limit switching for that session while output-based recovery remains active.
- Exact plan changes:
  - At `docs/plans/2026-04-29-aisup-supervisor-daemon.md:21`, clarify that discovering `claude_session_id` requires matching telemetry to the active `aisup_session_id` by launch time, current account, and cwd/project slug; it is not any freshest account telemetry.

#7 — Rehydration ignores persisted sessions whose tmux session disappeared
- Issue: `rehydrateSessions()` is described as starting from `tmux list-sessions`, reading state for discovered tmux sessions, and marking tmux-without-state sessions as orphans. It does not define the inverse reconciliation path: persisted non-terminal session state with no matching tmux session. That can happen if the tmux server/session is killed while the daemon is down, if the source session disappears during an interrupted switch, or if a user externally destroys the tmux session before daemon restart.
- Impact: After daemon restart, an `ACTIVE` or `SWITCH_PENDING_AT_IDLE` state file with no tmux session can be silently omitted from monitoring loops, leaving offline/status commands to report stale supervised state while no runner exists. `aisup start` should remain blocked by the preserved logical session after #1, but no recovery path runs to restart, switch, or exhaust it. This breaks daemon restart recovery and can trap the operator between “session already exists” and “nothing is supervised.”
- Fix: Make rehydration reconcile the union of persisted session state files and live tmux sessions, with persisted state authoritative for logical sessions. For every persisted session: if `switch_tx` is non-null, run switch recovery before normal reconciliation; if state is `ACTIVE` or `SWITCH_PENDING_AT_IDLE` and the tmux session is missing, emit `session.destroyed_externally`, scan the last 64KB of the output log if present for 429 classification, then apply the recovery decision matrix (same-account restart, account switch, or EXHAUSTED if no runnable target remains). If state is `CREATING`, `STOPPING`, or `SWITCHING` without enough transaction data, mark it as recoverable failed operation with typed status and require force stop/manual recovery rather than dropping it. If state is `STOPPED` with no tmux, it is reusable; if `STOPPED` has a live tmux session, use the #1 inconsistent/orphan recovery. Keep tmux-without-state sessions as orphans in status, but do not let orphan handling delete or supersede persisted logical sessions.
